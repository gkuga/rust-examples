## The core idea

> **`Pin` checks `Unpin`, not `PhantomPinned`.**
> `PhantomPinned` is just the simplest way to make a type `!Unpin`.

```
struct SelfRef { ..., _pin: PhantomPinned }
  -> PhantomPinned is !Unpin
  -> Unpin is an auto trait, so SelfRef is !Unpin too
  -> Pin's DerefMut / get_mut / into_inner require T: Unpin, so they are unavailable
  -> safe code cannot get &mut SelfRef, so it cannot move it (swap, move out, ...)
```

The bounds in `std` mention only `Unpin`:

```rust
impl<Ptr: Deref> Deref for Pin<Ptr> { ... }                        // &T: always
impl<Ptr: DerefMut<Target: Unpin>> DerefMut for Pin<Ptr> { ... }   // &mut T: only if T: Unpin
```

- `*pin` goes through the inner pointer: `*a` on `Pin<Box<SelfRef>>` is `SelfRef`.
  Reading (`&*a`, `a.x`) always works; writing (`&mut *a`, `a.x = 1`) needs `T: Unpin`.
- `Pin` does nothing at runtime (`#[repr(transparent)]`, zero cost). The value is not
  physically fixed: safe code *cannot* move it, and `unsafe` code (`get_unchecked_mut`)
  *promises not to*. Moving it there is undefined behavior.
- Moving the `Pin<Box<_>>` itself (`mem::swap(&mut a, &mut b)`) is fine: only the
  pointers move. Swapping the contents (`mem::swap(&mut *a, &mut *b)`) does not compile.
- Remove `_pin` and `SelfRef` becomes `Unpin`: `Box::pin` still compiles, but `Pin`
  restricts nothing and the swap breaks the self-reference again.
- `async` only makes the future `!Unpin`; it does not pin it. The future can be moved
  freely until it is pinned by `.await` (inside the already pinned parent) or by the
  executor (`Box::pin` / `pin!` before the first `poll`).

## Examples

| Run | What it shows |
|---|---|
| `cargo run` | The problem: a self-referential struct breaks when moved (the assert fails) |
| `cargo run --example box_not_enough` | `Box` alone is not enough: safe code can still swap or move the value out |
| `cargo run --example box_pinned` | Fixes `box_not_enough` with `Pin`: swapping or moving the contents no longer compiles |
| `cargo run --example pinned` | The fix: `PhantomPinned` + `Box::pin` keep `ptr` pointing to `x` after moves |
| `cargo run --example stack_pinned` | Same fix without `Box`: pin on the stack with `pin!`, then initialize in two steps |
| `cargo run --example unpin` | `Pin` only restricts `!Unpin` types; for `Unpin` types it is a no-op |
| `cargo run --example async_pin` | Why `Future::poll` takes `Pin<&mut Self>`: async blocks can be self-referential |

### Key points

- **`Pin<P>`** wraps a pointer (`&mut T`, `Box<T>`, ...) and promises that the pointee
  will not move again. Moving the `Pin` itself only moves the pointer.
- **`Unpin`** is an auto trait meaning "safe to move even when pinned". Almost every
  type is `Unpin`, so `Pin::new` and `Pin::get_mut` work and Pin changes nothing.
- **`!Unpin`** types (with `PhantomPinned`, or futures generated by `async`) cannot be
  unpinned in safe code: `Pin::new(&mut x)` and `get_mut()` do not compile.
  Pin them with `pin!` (stack) or `Box::pin` (heap).
- An async block that holds a reference to its own local across `.await` stores both
  the value and the reference in its state machine. That is why it is `!Unpin` and why
  `poll` requires `Pin<&mut Self>`.

## Unpin

Reference: [`std::marker::Unpin`](https://doc.rust-lang.org/std/marker/trait.Unpin.html)

> Types that do not require any pinning guarantees.

`Unpin` means "this type does not care about being pinned": moving it never breaks it.
For such a type, `Pin` has no effect:

> if `T: Unpin`, a value of type `T` will _not_ be bound by the invariants which pinning
> otherwise offers, even when "pinned" by a `Pin<Ptr>` pointing at it.

So the name is best read as "pinning-agnostic", not "unpinned".

### Pin vs Unpin

| | Who decides | Meaning |
|---|---|---|
| `Pin<P>` | the user of a value | "this value will not move from now on" |
| `Unpin` | the type itself | "I can move safely, so I don't need that promise" |
| `!Unpin` | the type itself | "I may break if moved, so keep the Pin promise" |

| | Moving breaks it? | Behavior inside `Pin` |
|---|---|---|
| `T: Unpin` | no | `Pin::new`, `get_mut`, `DerefMut` all work; `T` can still be moved |
| `T: !Unpin` | maybe | no safe way to get `&mut T`, so it cannot be moved (`get_unchecked_mut` is `unsafe`) |

### Auto trait

`Unpin` is an **auto trait** (like `Send` and `Sync`): the compiler implements it without
an explicit `impl`, based on the fields.

- A struct or enum is `Unpin` if **all of its fields are `Unpin`**.
- Almost every type is `Unpin`: primitives, `&T`, `&mut T`, raw pointers, `String`,
  `Vec<T>`, `HashMap<K, V>`, ...
- So a user-defined type such as `struct Value { n: u32, polled: bool }` is `Unpin`
  automatically, even though it never mentions `Unpin`.

```rust
struct SelfRef {
    x: u32,              // Unpin
    ptr: *const u32,     // Unpin (raw pointers are Unpin)
    _pin: PhantomPinned, // !Unpin
}                        // -> one !Unpin field makes SelfRef !Unpin
```

Without `_pin`, `SelfRef` would be `Unpin`, because the compiler cannot tell that `ptr`
points into the struct itself. Then `Pin` would not stop anyone from calling
`get_mut()` and `mem::swap`-ing two pinned values, which breaks the self-reference.

### Types that are not Unpin

- **`PhantomPinned`**: a zero-sized marker that is deliberately `!Unpin`. Adding it as a
  field is the stable way to opt out of `Unpin`. The docs put it this way:
  > It is the responsibility of the implementor of a type that relies upon pinning for
  > soundness to ensure that type is _not_ marked as `Unpin` by adding `PhantomPinned` field.
- **Futures generated by `async` blocks / `async fn`**: they may hold references to their
  own locals across `.await`, so the compiler makes them `!Unpin`. This is why they must be
  pinned (`pin!` / `Box::pin`) before calling `poll`.

### Pointers are Unpin regardless of the pointee

`Box<T>`, `Arc<T>`, and `Rc<T>` are `Unpin` even when `T` is not: moving the pointer does
not move `T`. For example, `Pin<Box<dyn Future>>` (`BoxFuture`) is `Unpin`, so a struct
holding one is `Unpin` as well. `Pin<P>` itself is `Unpin` when `P` is `Unpin`.

### Implementing it by hand

`impl Unpin for MyType {}` is allowed and is **safe**, since `Unpin` only relaxes `Pin`'s
API. It is used, for example, by future wrappers that never pin their inner future
structurally. The opposite (`impl !Unpin`) is unstable, so use `PhantomPinned` instead.

### How a type becomes !Unpin

Plain data never becomes `!Unpin` by accident. Every `!Unpin` type traces back to one of
these sources:

| Source | Did you opt out explicitly? |
|---|---|
| A `PhantomPinned` field | yes |
| A future generated by `async` | no (the compiler does it) |
| A field whose type is `!Unpin` (propagation) | no |

Propagation is the one that catches people out:

```rust
struct MyTask<F> {
    fut: F,                    // MyTask<F>: Unpin only if F: Unpin
}

struct Timeout {
    sleep: tokio::time::Sleep, // Sleep is !Unpin, so Timeout is !Unpin too
}
```

Storing the future as `Pin<Box<F>>` (e.g. `BoxFuture`) stops the propagation, because
`Pin<Box<_>>` is always `Unpin`.

### When to add PhantomPinned

Add it to any type that **breaks if its address changes**:

- **Self-referential types**: a field points into the same value (`SelfRef` in
  `examples/pinned.rs`, or the state machine generated by `async`).
- **Types whose address is stored elsewhere**: e.g. nodes of an intrusive linked list,
  where other nodes or a registry hold pointers to them. tokio's `Sleep` is `!Unpin`
  for this reason (timer entries are linked into the runtime's timer wheel).

The compiler cannot detect either case, so the implementor must opt out of `Unpin`.

In practice you rarely write such types by hand: it needs `unsafe` (e.g.
`get_unchecked_mut`), and a mistake is undefined behavior. Common alternatives:

- Store an **index** (e.g. into a `Vec`) instead of a pointer.
- Keep the pointed-to data in a separate allocation (`Box`, `Arc`) so moving the outer
  struct does not move it.
- Use a crate such as [`ouroboros`](https://crates.io/crates/ouroboros) or
  [`self_cell`](https://crates.io/crates/self_cell) for safe self-referential structs.
- If you only need to keep a reference across `.await`, just write an `async` block and
  let the compiler generate the self-referential, `!Unpin` future.

Writing `PhantomPinned` directly is mostly for low-level library code (async runtimes,
hand-written `Future`s). `examples/pinned.rs` is a hand-made reproduction of what `async`
does behind the scenes.
